## 1. Operating Rules

This plan converts the scientific controls in `Procedure.md` into implementation phases. The phases are sequential. I must not begin a phase until its predecessor's handoff criteria are satisfied, except for creating non-production scaffolding that cannot change data or results.

For **every phase**, I will:

1. create automated test cases before or alongside the implementation;
2. run the complete test suite, including all earlier tests;
3. require every test to pass before handoff;
4. retain test output, run identifier, configuration hash, and artifact hashes in the phase record; and
5. treat a failed test as a stop condition—not as a warning to be bypassed.

No web page, chart, map, rank, or export may claim that a location is eligible for enforcement, suitable for a camera, legally within a school zone, or certain to experience a future crash. The product is a retrospective, explainable historical prioritization aid for Norfolk.

## 2. Target Deliverable Architecture

```text
immutable public/acquired data snapshots
        ↓
validation and provenance pipeline
        ↓
cleaned records + exclusion ledger + validated school layer
        ↓
deterministic location assignment and feature engineering
        ↓
explainable score + validation/sensitivity artifacts
        ↓
versioned publication dataset and evidence bundle
        ↓
static web application / interactive map / downloadable documentation
```

The preferred publication model is a static web application, because the project is batch analytics and must remain viewable without a live backend. A generated map may use Folium or an equivalent open-source browser mapping library. The app shall consume only validated, versioned export files generated by the pipeline; it shall never recompute scores in the browser or expose raw records unnecessarily.

## 3. Phase 0 — Governance, Repository Scaffold, and Test Foundation

### Objective

Establish a deterministic, auditable project structure and a test harness before any analytic transformation or web presentation begins.

### Tasks

1. Create the implementation directory layout, keeping immutable inputs separate from generated artifacts:

   ```text
   data/raw/          # immutable source snapshots; no in-place edits
   data/staged/       # validated staging copies
   data/derived/      # cleaned, feature, score, and audit datasets
   configs/           # versioned run configurations
   src/               # pipeline modules
   tests/             # automated unit, integration, and regression tests
   outputs/runs/      # run-specific checkpoints, logs, and manifests
   web/               # static application source and generated public assets
   ```

2. Select a Python environment and record the runtime, operating system, and locked package versions. Use open-source dependencies only.
3. Add a commandable test runner and a separate command that executes the full pipeline from a configuration file.
4. Create a `run_manifest` schema containing `run_id`, input paths, SHA-256 hashes, source provenance, configuration hash, CRS, location-unit definition, score specification, seed, dependency versions, output paths, and timestamps.
5. Define an append-only structured-log format with stage name, input/retained/excluded row counts, exception class, hash status, and operating state.
6. Create a minimal synthetic fixture dataset that contains valid records and deliberate invalid cases: duplicate ID, malformed datetime, invalid coordinate, closed school, preschool, and transfer-limited ADT metadata. Fixtures must never be confused with production data.
7. Implement atomic-write helpers and run-directory creation so a failed run cannot overwrite a prior evidence bundle.
8. Add `.gitignore` coverage for generated caches, local environments, and non-public transient artifacts while retaining reproducibility configurations and test fixtures.
9. Document exact commands for installing dependencies, running tests, running a named configuration, and generating the web build.

### Mandatory test cases

- [ ] A new run creates a unique `run_id` and isolated output directory.
- [ ] Manifest validation rejects missing required fields and accepts a complete manifest.
- [ ] Configuration hashing changes when a score, CRS, location, or input setting changes.
- [ ] Structured logs contain all required fields for both success and controlled-failure paths.
- [ ] Atomic write leaves no partially promoted final artifact when an injected write failure occurs.
- [ ] Synthetic fixtures are marked as test-only and cannot be selected by a production configuration.
- [ ] The full test command runs successfully in a clean environment.

### Handoff criteria

- Repository layout, environment lock, manifest schema, logging contract, and test harness exist and are documented.
- All Phase 0 test cases and the complete test suite pass.
- A sample run produces a hashed manifest, log, and empty-but-valid artifact structure without touching raw source files.

## 4. Phase 1 — Source Intake, Provenance, and Immutable Baseline

### Objective

Create trusted, hash-verified snapshots of the Norfolk inputs and establish the descriptive baseline before any scoring.

### Tasks

1. Register the crash, elementary/preschool/kindergarten, middle/high/K–12, and ADT inputs in a source register.
2. Record source owner, acquisition method/date, public/licensing/provenance status, filename, size, row/feature count, and known limitations.
3. Compute SHA-256 for every raw input at intake and copy each source to a read-only archive/checksum location. Preserve the current ADT filename unless a deliberate, fully referenced rename is made.
4. Verify that the current ADT GeoJSON reports `exceededTransferLimit=true`; mark it unusable for exposure adjustment until a complete Norfolk-filtered, paginated extract has been independently verified.
5. Create an input inventory report that reconciles the documented baseline: 42,004 unique crash document numbers, 2016–2025 date coverage, 102 raw school records, and 92 records marked open, subject to programmatic confirmation.
6. Generate descriptive baseline tables for crash year, month, hour, severity, fatality, serious injury, pedestrian involvement, bicycle involvement, intersection type, and required-field missingness.
7. Capture the runtime and dependency versions used to produce the baseline.
8. Create the Phase 1 checkpoint, archive its logs/reports, and attach all hashes to the run manifest.

### Mandatory test cases

- [ ] SHA-256 verification detects a one-byte modification to an input fixture.
- [ ] The source register rejects an input lacking provenance status, acquisition date, or hash.
- [ ] Raw inputs remain byte-identical after the intake/baseline pipeline runs.
- [ ] Crash document-number uniqueness is checked and duplicate rows are surfaced, not silently discarded.
- [ ] Baseline date range, row counts, and null counts reconcile with the programmatic source scan.
- [ ] ADT parsing detects `exceededTransferLimit=true` and forces `exposure_enabled=false`.
- [ ] A source snapshot mismatch prevents the pipeline from proceeding to downstream stages.

### Handoff criteria

- Every analytic input has complete provenance metadata and a verified SHA-256 hash.
- The raw working copy and independent archive copy both pass hash verification.
- Baseline tables and an input reconciliation report exist; unexplained count differences are resolved or block the handoff.
- ADT exposure status is explicitly set to either verified-enabled or disabled. The current transfer-limited file must remain disabled.
- All Phase 1 and earlier tests pass.

## 5. Phase 2 — Data Quality, Cleaning, and Validated School Layer

### Objective

Transform validated snapshots into auditable derived datasets while preserving every source-row decision and constructing the active K–12 proximity layer.

### Tasks

1. Implement explicit schema contracts for crash CSV, both school CSVs, and optional ADT GeoJSON.
2. Parse crash datetimes deterministically; generate a reason-coded exclusion ledger for malformed or out-of-window records.
3. Validate crash identifiers, numeric fields, categorical values, coordinate finiteness, coordinate ranges, and declared CRS.
4. Apply the approved Norfolk boundary/buffer check. Retain excluded records in the ledger with a source identifier and reason, rather than deleting them.
5. Produce a cleaned crash table that has a stable source-row identifier and preserves raw field values needed for audit.
6. Combine the two school source files into a derived inventory while preserving original POI IDs, categories, source filename, and status.
7. Classify schools into elementary, middle, high, K–12, preschool, kindergarten, closed, unresolved, and other. Store the classification rationale and any manual adjudication evidence.
8. Build the primary school feature layer using active Norfolk elementary, middle, high, and K–12 facilities only. Keep preschool, kindergarten-only, closed, and unresolved facilities in an audit layer.
9. Investigate duplicate names at separate coordinates—including James Blair Middle School and Little Creek Elementary School—without automatically collapsing them. Record whether each coordinate is retained, excluded, or unresolved and why.
10. Confirm that crash and school data use compatible source coordinates; transform both to one documented meter-based projected CRS for distance calculations.
11. Create quality reports: schema results, exclusion counts, coordinate checks, school classification summary, duplicate-name ledger, and raw-to-derived row reconciliation.

### Mandatory test cases

- [ ] Schema contracts reject missing or renamed required columns.
- [ ] Malformed datetimes, null coordinates, non-finite coordinates, and out-of-bound coordinates receive deterministic reason codes.
- [ ] Retained crash rows plus excluded crash rows equal input crash rows exactly.
- [ ] No raw file is modified by cleaning.
- [ ] Closed facilities and preschool/kindergarten-only facilities are excluded from the primary K–12 feature layer but retained in the audit layer.
- [ ] An active elementary, middle, high, and K–12 fixture is included in the primary layer.
- [ ] Same-name facilities at distinct coordinates remain separate unless a specific adjudication rule and evidence record authorizes a change.
- [ ] Coordinate transformation preserves expected known-point geometry within the declared tolerance.
- [ ] Each derived row retains a source identifier, `run_id`, and transformation/version reference.

### Handoff criteria

- The cleaned crash table, exclusion ledger, combined school inventory, primary K–12 layer, and school audit layer have been produced and hash-verified.
- Every row is reconciled to a retained or reason-coded excluded state.
- The school layer's provenance, open/closed handling, and duplicate-campus decisions are documented.
- CRS and coordinate compatibility checks pass.
- All Phase 2 and earlier tests pass.

## 6. Phase 3 — Location Definition and Feature Engineering

### Objective

Choose one reproducible location unit and generate inspectable, provenance-linked features for each eligible Norfolk location.

### Tasks

1. Evaluate the available crash precision and roadway fields to select one location unit: derived intersection, corridor/segment, fixed grid, or deterministic spatial cluster.
2. Document the selection before inspecting any ranking: algorithm, CRS, input fields, spatial tolerance/grid size/cluster parameters, deterministic seed, boundary behavior, expected limitations, and the rationale for rejecting alternatives.
3. Implement a deterministic location-assignment routine that creates a stable location ID, geometry, human-readable label where defensible, and source-crash membership table.
4. Measure and report assignment rate. Records that cannot be assigned must remain reason-coded and must not be silently dropped.
5. Engineer separate feature tables for:
   - historical crash burden and harm;
   - fatalities, suspected serious injuries, and injury burden where available;
   - pedestrian and bicycle involvement;
   - hour-of-day and day-of-week concentration;
   - distance to nearest validated active K–12 facility; and
   - exposure-adjusted burden **only** if the ADT gate was verified in Phase 1.
6. Preserve raw counts alongside normalized values. Do not make zero counts or small denominators appear artificially precise.
7. Create a pre-declared sensitivity configuration for plausible location tolerances, grid resolutions, or normalizations. The primary configuration remains frozen.
8. Build the candidate-location data dictionary and a per-location lineage view linking each feature to source records and transformation version.

### Mandatory test cases

- [ ] The same input, configuration, seed, and environment yield identical location IDs and geometries on repeated execution.
- [ ] Location assignment is at least 99.5% for eligible crash records; every unassigned record has a reason code. If the threshold is not met, the test fails and blocks ranking.
- [ ] Known synthetic crash coordinates map to the expected location under the frozen algorithm.
- [ ] Boundary-edge records follow the declared inclusion rule consistently.
- [ ] Each feature has a defined formula, valid range, source lineage, and no undocumented missing value treatment.
- [ ] Nearest-school distance is calculated from the validated active K–12 layer only and uses the declared projected CRS.
- [ ] ADT-derived metrics cannot be produced when `exposure_enabled=false`.
- [ ] Feature generation preserves raw counts and does not modify prior checkpoints.
- [ ] Sensitivity configurations are recorded but cannot replace the primary configuration automatically.

### Handoff criteria

- Exactly one primary location unit is frozen in the manifest before score calculation.
- A complete candidate-location table, crash-membership table, feature table, and data dictionary exist.
- The location-assignment threshold and all feature-lineage tests pass.
- Exposure metrics are either fully traceable to complete verified ADT or absent from the feature table and public claims.
- All Phase 3 and earlier tests pass.

## 7. Phase 4 — Explainable Scoring and Ranked Output

### Objective

Produce a deterministic, interpretable Norfolk historical prioritization index without creating a deployment recommendation.

### Tasks

1. Choose the score method before examining ranked outputs. The default is the transparent weighted index specified in `Procedure.md`; any model alternative must meet the same per-location explanation standard.
2. Define and freeze each factor's formula, normalization, direction, caps/winsorization rules if used, weights, and missing-data treatment in the configuration.
3. Ensure factor weights sum to 1.0; set the exposure weight to zero when ADT is incomplete or disabled.
4. Calculate each location's component values and total score. Preserve intermediate values and precision sufficient for reproducibility.
5. Produce a ranked table with location ID, label, geometry reference, total score, all component contributions, raw supporting counts, nearest qualifying school distance, data-quality flags, and an explanation string.
6. Add a mandatory limitation label to every output: `historical prioritization aid; not a legal, causal, camera-deployment, or eligibility determination`.
7. Generate top-N, full-rank, and non-rankable-location outputs. Do not suppress inconvenient rows without an explicit rule.
8. Save configuration, feature table, score table, and a hash-verified checkpoint. Do not circulate results externally until Phase 5 validation succeeds.

### Mandatory test cases

- [ ] Score calculation is deterministic and repeated runs produce identical row-level values.
- [ ] Weights sum to 1.0 within a declared floating-point tolerance; invalid weights fail validation.
- [ ] A disabled exposure feature has an exactly zero contribution and cannot affect rank.
- [ ] Synthetic fixtures with known feature values generate expected component and total scores.
- [ ] Every rankable location has all required component values, source lineages, and an explanation string.
- [ ] Every top-10 location has a complete data-backed explanation and limitation label.
- [ ] Sort order, tie-break rule, and non-rankable handling are deterministic and documented.
- [ ] Score exports retain `run_id`, configuration hash, input-hash references, and output hash.
- [ ] Any change to the scoring configuration produces a new run and invalidates prior result hashes.

### Handoff criteria

- A frozen, interpretable scoring specification and deterministic ranked output exist.
- Every top-10 and every published row is explainable through component contributions and source evidence.
- Exposure is omitted unless its completeness gate has passed.
- All Phase 4 and earlier tests pass; no ranking is publicly released yet.

## 8. Phase 5 — Scientific Validation, Sensitivity Analysis, and Reproducibility

### Objective

Test whether the output satisfies the pre-registered data-integrity, stability, sensitivity, and reproducibility criteria in `Procedure.md`.

### Tasks

1. Execute a clean rerun from the archived raw inputs and frozen configuration. Compare manifests, row-level outputs, and hashes.
2. Perform the stratified manual quality audit using the documented random seed: at least 5 records in every non-empty selected stratum, capped at 100 total records; audit all records in strata smaller than 5.
3. Calculate audit agreement and the two-sided 95% Wilson confidence interval. The target is at least 98% agreement with lower CI bound at least 90%.
4. Perform temporal validation using pre-declared chronological blocks, normally 2016–2018, 2019–2021, and 2022–2025. Do not use future data in earlier-block scoring.
5. For locations meeting the frozen minimum event count, calculate adjacent-block Spearman rank correlation, two-sided p-value, bootstrap 95% CI, and top-10 Jaccard overlap.
6. Execute leave-one-year-out and documented pandemic-era sensitivity analyses. Retain all results, including unfavorable ones.
7. Execute spatial/location sensitivity configurations established in Phase 3 and compare top-10 overlap. Identify any ranking reversal caused by a defect.
8. Conduct a blinded top-and-bottom location review: inspect geometry and lineage before viewing rank; record defects separately from plausibility impressions.
9. Record all deviations, incidents, failed tests, remediation, and reruns in the FMEA/incident log.
10. Classify the pilot as validated feasibility, conditionally feasible, or not yet feasible according to the procedure's decision rules.

### Mandatory test cases

- [ ] A clean rerun from archived inputs produces identical row-level values and output hashes, or an approved deterministic-serialization exception is documented.
- [ ] Audit sampling is reproducible from the recorded seed and honors the stratification/cap rules.
- [ ] Agreement and Wilson CI calculations match known reference examples.
- [ ] Temporal blocks are non-overlapping and preserve chronological separation.
- [ ] Spearman, bootstrap CI, and Jaccard implementations return known results on synthetic rank fixtures.
- [ ] Validation output fails the release gate when ρ < 0.70, p ≥ 0.05, audit agreement <98%, CI lower bound <90%, or Jaccard overlap <0.60 where applicable.
- [ ] Sensitivity results cannot overwrite or silently replace the primary ranking.
- [ ] An unresolved integrity, provenance, spatial, reproducibility, explainability, or interpretation breach triggers an `ABORTED` release state.

### Handoff criteria

- The reproducibility, audit, temporal-stability, sensitivity, and blinded-review reports are complete and hash-verified.
- All thresholds pass, or the product is accurately classified as conditionally feasible/not yet feasible with the non-passing criterion prominently disclosed.
- No abort criterion is open.
- All Phase 5 and earlier tests pass.

## 9. Phase 6 — Web Application and Public Visualization

### Objective

Make the validated Norfolk output showcasable to non-technical visitors through a clear, accessible, static web application that lets people visualize the analysis without misrepresenting its scope.

### Required user experience

The application must allow a visitor to:

1. understand, before interacting with a rank, that the project is a historical prioritization aid and not a camera-deployment recommendation;
2. view an interactive Norfolk map of rankable locations or aggregate risk visualization;
3. inspect a searchable/sortable ranked table;
4. select a location and see its total score, factor contributions, raw supporting counts, nearest qualifying school distance, data-quality flags, and plain-language explanation;
5. view methodology, source inventory, data date range, limitations, and whether ADT exposure adjustment was omitted;
6. access downloadable CSV/JSON evidence and the final manifest/validation summary; and
7. view the pilot status as **validated feasibility**, **conditionally feasible**, or **not yet feasible**—never as deployment-ready.

### Tasks

1. Select a static web implementation compatible with the existing open-source project plan. Keep it separate from the pipeline and build it only from finalized publication artifacts.
2. Define a versioned web-data contract for the map/table/detail view. Include `run_id`, source-data cutoff, total score, factor contributions, flags, geometry, explanation, and limitation text.
3. Build the landing page with the project purpose, Norfolk boundary, data window, independent-project statement, and a persistent limitation banner.
4. Build the map view with a visible legend, accessible color scale, clustering/aggregation appropriate to the chosen location unit, and a control to reset filters.
5. Build the ranked-table view with sort, search, filter, pagination/virtualization when necessary, and a link from every row to the location detail.
6. Build the location detail panel/page. It must show factor contributions and data provenance rather than only a single score.
7. Build a methodology and limitations page that links to the pilot procedure, execution plan, data dictionary, validation report, source register, and reproducibility instructions.
8. Build a downloads section for final artifacts. Exclude raw sensitive/unnecessary detail; publish only the reviewed release bundle.
9. Display data quality warnings in the interface, including `EXPOSURE_ADJUSTMENT_NOT_APPLIED` when ADT is incomplete.
10. Implement responsive layout, keyboard navigation, semantic headings, visible focus states, adequate text/background contrast, and non-color-only interpretation of risk levels.
11. Add build metadata to the site: release `run_id`, artifact hash/version, source cutoff, and generation timestamp.
12. Produce a static production build and test it via a local static server before publishing it through the repository's selected hosting workflow.

### Mandatory test cases

- [ ] Web-data schema validation rejects a missing `run_id`, score component, explanation, limitation, or geometry field required by the selected view.
- [ ] Every displayed map/table location resolves to a row in the final hash-verified publication dataset.
- [ ] The app displays the limitation banner on landing, map, table, and location-detail views.
- [ ] When ADT is disabled, the interface displays the exposure limitation and does not label any metric a crash rate.
- [ ] Location details show total score, all factor contributions, supporting values, source/run metadata, and data-quality flags.
- [ ] Map legend, filters, table sorting, search, and row-to-detail navigation work on representative fixtures and final build data.
- [ ] Keyboard-only navigation can reach and operate all controls; visual focus is visible; map information has a non-map/tabular alternative.
- [ ] Responsive checks pass at common mobile, tablet, and desktop viewport widths without hidden critical content or horizontal overflow.
- [ ] Broken/missing web-data assets yield a clear unavailable-state message and do not show stale or fabricated ranks.
- [ ] Production build succeeds from a clean checkout/environment and renders through a local static server without console errors.
- [ ] A content review test rejects prohibited deployment, legal, causal, vendor-affiliation, or certainty language.

### Handoff criteria

- A production static build is generated exclusively from final, validated publication artifacts.
- The app exposes map, ranked table, detailed explanation, methodology, limitations, and downloadable evidence.
- Accessibility, responsiveness, integrity, and prohibited-claim tests all pass.
- All Phase 6 and earlier tests pass.

## 10. Phase 7 — Release, Showcase, and Post-Release Monitoring

### Objective

Publish an evidence-backed, shareable demonstration while preserving the full audit trail and preventing post-release changes from silently altering results.

### Tasks

1. Assemble the final release bundle: run manifest, input/output hashes, source register, exclusion and school-classification ledgers, location specification, feature table, ranked table, validation report, FMEA incident summary, data dictionary, web build, and reproducibility instructions.
2. Generate a release manifest that hashes every published artifact and references the frozen input snapshot and configuration.
3. Conduct final content review for accuracy, non-claims, independent-project status, cited sources, and accessible explanations.
4. Conduct a reader walkthrough with a non-technical reviewer where available. Ask them to explain the product purpose and limitations; record misunderstandings and correct them before release.
5. Publish the static web application and repository artifacts through the selected hosting workflow. Confirm the public build serves the expected release version.
6. Verify that a visitor can reach the map, inspect a location, read limitations, download the evidence bundle, and identify the run/version.
7. Create a release note stating the Norfolk-only scope, data window, analytical status, ADT exposure status, and pilot classification.
8. If any source or configuration changes after release, create a new `run_id`, rerun all downstream phases, and publish a new version. Never patch published ranks by hand.
9. Monitor only operational presentation health (asset availability, broken links, rendering errors). Do not turn the batch pilot into an ungoverned live system.

### Mandatory test cases

- [ ] Release-manifest hashes match each published artifact exactly.
- [ ] The published site version/run ID matches the approved release bundle.
- [ ] Public navigation reaches map, table, detail, methodology, limitations, and downloads without broken links.
- [ ] A fresh environment can follow the published reproducibility instructions and obtain the approved output.
- [ ] The final content scan finds no prohibited claim or missing limitation statement.
- [ ] Introducing a changed source/configuration causes a new `run_id` and prevents overwrite of the previous release.
- [ ] The complete test suite, including end-to-end web smoke tests, passes against the release candidate.

### Handoff criteria

- The Norfolk pilot is showcasable as a working web application with transparent methodology and downloadable evidence.
- The final release bundle is immutable, hash-verified, and reproducible.
- All Phase 7 and all prior automated, integration, accessibility, content, and end-to-end tests pass.
- The final published language accurately represents the pilot classification and never exceeds the documented scientific or legal scope.

## 12. Definition of Done

The pilot is complete only when all execution phases have passed their handoff criteria and the final static web application enables the public to inspect **what was analyzed, how the score was formed, what its limitations are, and which evidence supports each displayed location**. A visually polished map without a passing, reproducible, explainable data pipeline is not a completed Sentinel-VA pilot.
